## Outcome

Measured 2026-08-09; scored 2026-08-10, after `allclose` stopped gating operations the
manuscript states no standard for. The measurements in `results/` are untouched — only the
verdicts moved, which is what re-scoring a stored run is for.

- Method groups passing: 15/20
- Gating metrics passing: 139/150
- Measurements recorded as evidence: 243
- Scripts producing a result record: 20/20

All 20 scripts completed. A script exiting non-zero would mean it failed to produce a record at
all; a missed criterion is reported by `evaluate.py` instead, which is why the script count and
the criterion count now say different things.

## This snapshot is self-contained

`results/` holds the **enriched** records: every comparison `evaluate.py` derived from the
stored arrays is written back as a scalar. So the snapshot re-scores without the arrays and
without a GPU, and reproduces the numbers above exactly:

```bash
python benchmarks/comparison/evaluate.py --results benchmarks/comparison/snapshots/2026-08-09-derived/results
```

The raw Zarr stores are **not** committed — 158 MB for this run, and they belong with the run
rather than in the repository. They are what allows a _new_ comparison to be computed later; the
scalars here are what allows this verdict to be checked.

## Reading the failures

[`NUMERICAL_VALIDATION.md`](../../../../NUMERICAL_VALIDATION.md) assesses all nine comparisons
that exceed the `allclose` envelope — the four that gate and the five recorded as evidence —
including which term of the criterion decided each one and how thin the failing tail is. [`OPEN.md`](../../../../OPEN.md) covers the
stochastic failures and the limits of the evidence as a whole. Thresholds are not widened to
make a run green.
